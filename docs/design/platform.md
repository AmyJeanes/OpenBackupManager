# Platform layer

What each OS does its own way, such as notifications, secrets, starting at login and PATH, sits behind interfaces in Core, with one implementation for each OS. Choosing where secrets go, and moving them, is in the guide's [Settings](../guide/settings.md#secret-store) and [Command line](../guide/command-line.md).

## Code map

- `OpenBackupManager.Core`'s `Platform` folder: the interfaces (`INotifier`, `ISecretStore`, `IStartAtLogin`), `Notification`, `SecretName`, and `FileStore`, the `file` store, which is the same on every OS. `SystemPrograms` finds the OS's own programs.
- `OpenBackupManager.Platform.Windows`: `WindowsNotifier` with `Toast` and `NotificationActivator`, `CredentialManager`, `RunKey`, `UserPath`, `DesktopShell` and `CrashRestart`. It has no UI, so the Windows app and the engine can both use it.
- `OpenBackupManager.Platform.MacOS` has `Keychain`, and `OpenBackupManager.Platform.Linux` has `SecretService`. Each platform project's `AddWindowsPlatform`, `AddMacOSPlatform` or `AddLinuxPlatform` registers its secret store, which `obmd` calls for the OS it's built on.
- The engine's `Secrets` picks the store from `secret-store`, and moves secrets between stores for `obm secrets migrate`. Everything else in the engine goes through it rather than the stores.
- The Keychain and Secret Service tests make a keychain or keyring of their own for each test, so they run on any Mac or Linux desktop without touching the real one.

## Interfaces and builds

- **Interfaces in Core.** The engine keeps the secrets, and the shared view models say what each notification shows, so neither interface can live with an app. What only Windows has, such as `DesktopShell` and `UserPath`, has no interface.
- **`obmd` is built for Windows' own framework on Windows.** Platform.Windows needs it for Windows' toast API, and a project for plain `net11.0` can't reference one that needs it. So `obmd`, and `Cli.Tests`, which run it, pick their framework by the OS they're built on, and `obmd` references each OS's platform project only when it's built on that OS, as its packages are, since [NativeAOT can't build for another OS](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/cross-compile). Anything else checks the OS at run time, with `[SupportedOSPlatform]` so the analyzer checks the callers.
- **CsWin32 generates the COM interfaces too, as a build task.** `DesktopShell` and `NotificationActivator` talk to Explorer and Windows' notifications through COM, and [NativeAOT has no built-in COM support](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/#limitations-of-native-aot-deployment), so COM goes through `ComWrappers`, which .NET's COM source generators write for us. CsWin32 can generate interfaces for those, but [only when it writes its code before compiling](https://github.com/microsoft/CsWin32/blob/v0.3.371/docfx/docs/getting-started.md#enable-cswin32runasbuildtask), so Platform.Windows sets `CsWin32RunAsBuildTask`, as the Windows app does for consistency. It also sets `DisableRuntimeMarshalling`, as CsWin32 recommends, so the source generators do every conversion.
- **What a program prints is disposed by whatever reads it.** [Disposing a `Process`](https://github.com/dotnet/runtime/blob/v11.0.0/src/libraries/System.Diagnostics.Process/src/System/Diagnostics/Process.cs#L843-L867) leaves the `StandardOutput` and `StandardError` it handed out open until a GC. .NET 11's [`Process.RunAndCaptureText`](https://github.com/dotnet/runtime/blob/v11.0.0/src/libraries/System.Diagnostics.Process/src/System/Diagnostics/Process.Scenarios.cs#L234-L250) leaves them open the same way, with no way to dispose them, so it isn't used.

## Notifications

- **Notifications are plain data, and what they say lives in the view models.** Each OS's notifier only has to show a title, text and buttons, and every app shows the same notifications, translated once, with their clicks tested on every OS.
- **Notifications use Windows' own toast API, not the Windows App SDK's.** The SDK's show nothing when the app runs elevated ([microsoft/WindowsAppSDK#3595](https://github.com/microsoft/WindowsAppSDK/issues/3595)), as everything does on GitHub's runners, so they couldn't be tested in CI. They also needed three workarounds: the builder didn't escape button labels ([#4996](https://github.com/microsoft/WindowsAppSDK/issues/4996)), its buttons couldn't close a notification without starting the app ([#2960](https://github.com/microsoft/WindowsAppSDK/issues/2960)), and registering needed a DLL that self-contained apps don't ship, so the runtime had to be installed ([#6774](https://github.com/microsoft/WindowsAppSDK/issues/6774)). The cost is doing the SDK's registration ourselves: the app's ID, the COM class for clicks, and removing both when uninstalling. It also keeps Platform.Windows free of the Windows App SDK.

## Secrets

- **The secret store is chosen, never guessed, on Linux.** With lingering on and nobody signed in, gnome-keyring is started but stays locked, so saving fails and reading a secret that's there says it's missing. After an automatic sign-in, reading waits on an unlock prompt. [Kopia turns the keyring off on Linux](https://github.com/kopia/kopia/blob/v0.23.1/cli/password_linux.go#L8) by default, as it doesn't work reliably in terminal sessions, and [Git Credential Manager has no Linux default](https://github.com/git-ecosystem/git-credential-manager/blob/v3.0.2/docs/credstores.md). Windows and macOS default to their own store, as theirs are unlocked whenever you're signed in at the desktop, which is when the engine usually runs. Over SSH they can't be used either: the login keychain is locked, and Credential Manager has nothing to keep secrets with.
- **Names from the home folder's key.** Copies with different homes run side by side, so they mustn't share secrets.
- **The file store is in the state folder, not the config folder.** `config.toml` is meant to be safe to share or keep in a dotfiles repo, so secrets stay out of its folder on macOS and Linux. Windows keeps both in one folder, so sharing that whole folder would share the secrets too.
- **Credential Manager, as Git Credential Manager uses.** It's built into Windows, [encrypted for the user in their profile](https://learn.microsoft.com/en-us/windows-server/security/windows-authentication/credentials-processes-in-windows-authentication#windows-vault-and-credential-manager), and visible and removable in Control Panel. `CredentialManager` is based on Git Credential Manager's store, keeping what it learned.
- **The Keychain through `/usr/bin/security`, not Security.framework.** Builds aren't signed with a stable identity, so [macOS can't tell an update from a different app](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements), and refuses it an item the previous build saved through Security.framework, or [asks for the login keychain's password](https://developer.apple.com/documentation/security/access-control-lists) (probed on macOS 15.8). An item the tool saved belongs to the tool, so every build reads it without a prompt. [go-keyring](https://github.com/zalando/go-keyring/blob/v0.2.8/keyring_darwin.go#L29), which gh and Kopia use, does the same.
- **Secret Service over D-Bus, not through libsecret or `secret-tool`.** [go-keyring](https://github.com/zalando/go-keyring/blob/v0.2.8/keyring_unix.go#L1-L9), which gh and Kopia use, talks to it over D-Bus too, with no native library to install. libsecret is a C library built on GLib, so reading the keyring's `Locked` property through it takes several native calls, and it isn't always installed on a server. `secret-tool` can't say whether the keyring is locked, and [reports a secret in a locked one as missing](https://gitlab.gnome.org/GNOME/libsecret/-/blob/0.21.7/tool/secret-tool.c#L226-L236) (probed on Ubuntu 26.04), which is exactly what the engine has to tell apart.
- **Moving secrets copies them before it removes any.** Removing them first could leave the engine on an empty store, and changing the setting last of all could leave it reading the old store once they're gone from it. In this order, wherever it stops, the setting points to a store that holds them all. What the new store already has for this home is kept, as it can be the only copy of a secret, such as after `secret-store` was changed by hand.

## Starting at login

- **The `Run` key for starting at login.** It needs no admin rights, and it's what [Windows' Startup apps](https://support.microsoft.com/en-us/windows/configure-startup-applications-in-windows-115a420a-0bff-4a6f-90e0-1934c844e473) lists and lets the user turn off. A scheduled task can start an app at login too, but it's for running elevated or on a schedule, which the app doesn't need. A packaged app's [`StartupTask`](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.startuptask) needs the app to be packaged, which it isn't.
- **Turning it off in Startup apps is left to Windows.** Windows marks the entry off under the same name in `Explorer\StartupApproved\Run`, so the app can write its entry at every start without undoing that. The app never reads or writes that mark, as it isn't a documented API.

## Built ourselves

- **No package does what the secret stores do (checked Nov 2026).** On macOS, every one found saves through Security.framework, which unsigned builds can't read after an update: ktsu.CredentialCache, Darkspyre.SecureStore, Devlooped.CredentialManager (Git Credential Manager's stores, repackaged), KeySharp and MSAL's cache extensions. On Linux they load libsecret or run `secret-tool`, apart from [Ace4896.DBus.Services.Secrets](https://github.com/Ace4896/DBus.Services.Secrets/blob/1.6.0/src/DBus.Services.Secrets/Item.cs#L155-L163), which is built on Tmds.DBus.Protocol as ours is, but unlocks a locked keyring, which can show a prompt, takes no cancellation token, and only connects to the session bus, so the tests' own bus can't be used. On Windows, [Meziantou.Framework.Win32.CredentialManager](https://github.com/meziantou/Meziantou.Framework/blob/0f1b40cf5b7009bd4d4863ab465edbe5e86914ea/src/Meziantou.Framework.Win32.CredentialManager/CredentialManager.cs#L48-L66) comes closest, but a read that fails for any reason comes back as not found, so over SSH it would say a secret is missing rather than why.
- **Windows' own integration code is ours too (checked Nov 2026).** No current library shows toasts for an unpackaged app running elevated with NativeAOT: DesktopNotifications is archived, and the others wrap the archived Community Toolkit's. [AutoLaunch](https://github.com/Linlccc/AutoLaunch/blob/v1.0.1/src/Platforms/WindowsRegistry.cs#L10-L17), for the `Run` key, marks its entry as allowed in `StartupApproved\Run` every time it's turned on, overriding someone who turned it off in Startup apps. The Windows App SDK's [`EnvironmentManager.AppendToPath`](https://github.com/microsoft/WindowsAppSDK/blob/v2.6.5/dev/EnvironmentManager/API/Microsoft.Windows.System.EnvironmentManager.cpp#L209-L241) finds an existing entry with a case-sensitive substring match, leaves a trailing `;`, and always writes `REG_EXPAND_SZ`, which `UserPath` avoids. Nothing packages starting a program through Explorer.

## Accepted limits

- **Any program running as the user can read their secrets** from Credential Manager, and from the Keychain through the `security` tool while they're signed in. Both stores keep secrets from other accounts, not from the user's own programs.
- **Moving a home to another folder leaves its secrets behind,** as their names come from the folder, so you'd sign in again.
- **A secret has a size limit in each OS's store:** 1,280 characters in Credential Manager, and about 2,990 bytes as UTF-8 in the Keychain, a little less with a long name, as its command has to fit in one of the `security` tool's lines.
- **Keychain Access shows a secret as base64,** as that's how it's saved.
