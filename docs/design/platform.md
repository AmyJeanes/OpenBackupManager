# Platform layer

What each OS does its own way sits behind interfaces in Core's `OpenBackupManager.Core.Platform`, with one implementation for each OS. Windows' are in `src/OpenBackupManager.Platform.Windows`, which has no UI, so the Windows app and later `obm` can both use it. macOS and Linux get theirs with their apps.

## How it works

- `INotifier` shows desktop notifications. A `Notification` has a title, lines of text, an action for clicking it, and buttons: an `ActionButton` passes its action back through `Clicked`, a `LinkButton` opens a link, and a `DismissButton` closes the notification. `Clicked` is raised through the synchronization context the notifier was created on, which in the app is the UI thread's. What the app's notifications say, and what clicking them does, is `AppNotifications` in the shared [view models](view-models.md).
- `WindowsNotifier` shows them through Windows' own toast API, with `Toast` making their XML. Each time the app starts, it registers its ID with Windows under `HKCU\Software\Classes\AppUserModelId`, with its name, its icon and `NotificationActivator`, the COM class Windows calls when a notification or one of its buttons is clicked. The installed app uses the ID Velopack gives its Start menu shortcut, and a copy that wasn't installed uses one made from its path. The COM class's ID is made from the app's ID, so each copy keeps one registration. While the app runs, clicks come back to it. After Quit, Windows starts it with the command registered for the COM class, which keeps its home, and it does what the click asked for, such as opening the main window, without opening the flyout. For now the tray menu has Show test notification, a placeholder sync failure whose View details button opens the main window, as does clicking the notification itself.
- `ISecretStore` keeps secrets, such as the rclone config password, by name, so `config.toml` can refer to them without holding them. Values go in and out as Core's `Secret`, so they never reach the logs.
- `IStartAtLogin` starts the app when the user signs in. Each app decides whether it should, and turns it on or off.
- `RunKey` does it with an entry in the user's `Run` key, `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, named from the home folder's key like the secrets, so each copy has its own. `RemoveFor` removes every entry that starts a given exe, whatever its home, for uninstalling.
- `CredentialManager` keeps them as generic credentials in Windows' Credential Manager, where Windows encrypts them for the user and keeps them to this computer. Each is named `OpenBackupManager-<key>/<name>`, where the key is made from the home folder's path, the same as the single-instance lock's, so the installed app, dev builds and test homes never see each other's. A secret can be up to 1,280 characters. The entries show in Control Panel's Credential Manager, under Windows Credentials.

## Why

- **Interfaces in Core.** The engine and `obm` will need secrets, and on macOS and Linux `obm` shows notifications itself, so neither interface can live with an app.
- **Notifications are plain data, and what they say lives in the view models.** Each OS's notifier only has to show a title, text and buttons, and every app shows the same notifications, translated once, with their clicks tested on every OS.
- **Notifications use Windows' own toast API, not the Windows App SDK's.** The SDK's show nothing when the app runs elevated ([microsoft/WindowsAppSDK#3595](https://github.com/microsoft/WindowsAppSDK/issues/3595)), as everything does on GitHub's runners, so they couldn't be tested in CI. They also needed three workarounds: the builder didn't escape button labels ([#4996](https://github.com/microsoft/WindowsAppSDK/issues/4996)), its buttons couldn't close a notification without starting the app ([#2960](https://github.com/microsoft/WindowsAppSDK/issues/2960)), and registering needed a DLL only shipped inside the runtime's MSIX ([#6774](https://github.com/microsoft/WindowsAppSDK/issues/6774)). The cost is doing the SDK's registration ourselves: the app's ID, the COM class for clicks, and removing both when uninstalling. It also keeps Platform.Windows free of the Windows App SDK.
- **Credential Manager, as Git Credential Manager uses.** It's built into Windows, encrypted for the user with DPAPI, and visible and removable in Control Panel. `CredentialManager` is based on Git Credential Manager's store (MIT licence, credited in `THIRD-PARTY-NOTICES.md`), keeping what it learned: secrets as UTF-16, as Windows' own tools read them, and kept to this computer rather than roaming with the user's account.
- **The `Run` key for starting at login.** It needs no admin rights, and it's what Windows' Startup apps lists and lets the user turn off. A scheduled task can start an app at login too, but it's for running elevated or on a schedule, which the app doesn't need. A packaged app's `StartupTask` needs the app to be packaged, which it isn't.
- **Turning it off in Startup apps is left to Windows.** Windows doesn't remove the entry, but marks it off under the same name in `Explorer\StartupApproved\Run`, and skips it at login. So the app can write its entry at every start without undoing that, as long as the name stays the same. The app never reads or writes that mark, as it isn't a documented API.
- **Names from the home folder's key.** Copies with different homes run side by side, so they mustn't share secrets. Moving a home to another folder leaves its secrets behind, so you'd sign in again.
