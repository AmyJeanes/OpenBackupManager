# Platform layer

What each OS does its own way sits behind interfaces in Core's `OpenBackupManager.Core.Platform`, with one implementation for each OS. Windows' are in `src/OpenBackupManager.Platform.Windows`, which has no UI, so the Windows app and the engine can both use it. Its `AddWindowsPlatform` registers the engine's, and `obmd` calls it when it's built for Windows. macOS' are in `src/OpenBackupManager.Platform.MacOS`, whose `AddMacOSPlatform` `obmd` calls when it's built for macOS, and Linux' in `src/OpenBackupManager.Platform.Linux`, with `AddLinuxPlatform`.

## How it works

- `INotifier` shows desktop notifications. A `Notification` has a title, lines of text, an action for clicking it, and buttons: an `ActionButton` passes its action back through `Clicked`, a `LinkButton` opens a link, and a `DismissButton` closes the notification. `Clicked` is raised through the synchronization context the notifier was created on, which in the app is the UI thread's. What the app's notifications say, and what clicking them does, is `AppNotifications` in the shared [view models](view-models.md).
- `WindowsNotifier` shows them through Windows' own toast API, with `Toast` making their XML. Each time the app starts, it registers its ID with Windows under `HKCU\Software\Classes\AppUserModelId`, with its name, its icon and `NotificationActivator`, the COM class Windows calls when a notification or one of its buttons is clicked. The installed app uses the ID Velopack gives its Start menu shortcut, and a copy that wasn't installed uses one made from its path. The COM class's ID is made from the app's ID, so each copy keeps one registration. While the app runs, clicks come back to it. After Quit, Windows starts it with the command registered for the COM class, which keeps its home, and it does what the click asked for, such as opening the main window, without opening the flyout. For now the tray menu has Show test notification, a placeholder sync failure whose View details button opens the main window, as does clicking the notification itself.
- `ISecretStore` keeps secrets, such as the rclone config password, by name, so `config.toml` can refer to them without holding them. Values go in and out as Core's `Secret`, so they never reach the logs. Each store also lists the names its home has saved, so they can all be moved or removed. A store any program can save to only lists items named exactly as it saves them. The engine reads and writes them; the apps and `obm` go through it.
- The engine's `Secrets` picks the store from `secret-store`, or with it left out, the OS's own: Credential Manager on Windows and the Keychain on macOS. Linux has no default, as Secret Service can't be read while you're not signed in with your password. Only this OS's stores are allowed values, so naming another OS's store is a mistake in `config.toml`, which stops the engine starting. Each store is registered under its `SecretStoreKind`, and `Secrets` reads the setting on every use, so a change applies straight away. Everything else in the engine reads, saves and removes secrets through `Secrets`, not the stores, so it can make them wait while secrets are being moved. `obm status` says which store is in use.
- `obm secrets migrate <store>` asks the engine to move this home's secrets, which `Secrets` does holding its lock throughout: it lists the old store, copies each secret and reads it back to compare, changes `secret-store` in `config.toml` and applies it at once, and only then removes them from the old store. A failure before the setting changes puts the new store back as it was, removing new copies and saving again any value a copy replaced, and says what failed. One that can't be removed afterwards is named, and `obm` exits with 1. Moving to the store in use does nothing; with none chosen yet, on Linux, it only sets `secret-store`. While `OBM_SECRET_STORE` is set, it refuses and says how to move them instead.
- Secret names are checked by Core's `SecretName` in every store: up to 64 lowercase letters, digits and dashes. A newline would split the Keychain's `security -i` command, and Credential Manager ignores case.
- `FileStore` is the `file` store, the same on every OS: `secrets.json` in the state folder, listing its keys, only readable by the user on macOS and Linux (0600), and on Windows by the user, SYSTEM and Administrators, set on the file itself rather than inherited, as the folder may let others in. Each change writes a new file beside the old one, flushed to disk, and renames it over it, so a crash or power cut never leaves it half written. The new file is always made afresh, so a file or link left in its place is never written through. A file that isn't valid JSON, or has a secret with no value, is refused rather than replaced, which would lose every secret in it. Only the engine uses it, so there's one writer. It's no better protected than its folder, and a backup or synced copy of the folder has the secrets in plain text.
- `IStartAtLogin` starts the app when the user signs in. Each app decides whether it should, and turns it on or off.
- `RunKey` does it with an entry in the user's `Run` key, `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, named from the home folder's key like the secrets, so each copy has its own. `RemoveFor` removes every entry that starts a given exe, whatever its home, for uninstalling.
- `CredentialManager` keeps them as generic credentials in Windows' Credential Manager, where Windows encrypts them for the user and keeps them to this computer. Each is named `OpenBackupManager-<key>/<name>`, and listed with `CredEnumerate` filtered to `OpenBackupManager-<key>/*`, where the key is made from the home folder's path, the same as the single-instance lock's, so the installed app, dev builds and test homes never see each other's. A secret can be up to 1,280 characters. The entries show in Control Panel's Credential Manager, under Windows Credentials. Any program running as the user can read them. A network sign-in, such as over SSH, has no credentials for Credential Manager to keep them with, so Windows refuses with `ERROR_NO_SUCH_LOGON_SESSION`, and the error says to use the `file` store instead. Windows' calls aren't async, so each finishes before its task is returned, with any error in the task.
- `Keychain` keeps them in the login keychain through Apple's `/usr/bin/security` tool, named like Credential Manager's: each item's service is `OpenBackupManager-<key>/<name>` and its account is the name. Every command names the login keychain's file, rather than leave it to the default keychain and search list, which the user can change. A call that takes over 30 seconds fails, and the tool is stopped when a call times out or is cancelled. Each secret is saved as base64, written to `security -i`'s input so it never appears in a command line, which any program can see. A secret can be up to about 2,990 bytes as UTF-8, a little less with a long name, as its command has to fit in one of the tool's 4,095-byte lines. Over SSH the login keychain is locked, so reading a secret says so. Listing reads `security dump-keychain`, which prints every item's attributes and none of their secrets, even from a locked keychain, without a prompt. `KeychainTests` make a keychain of their own for each test, as the login keychain is made, so they run on any Mac without touching the real one.
- `SecretService` keeps them in the desktop's keyring, such as GNOME Keyring or KDE Wallet, through the Secret Service API on the session's D-Bus, in its default keyring, which is the login one. Each item's label and `service` attribute are `OpenBackupManager-<key>/<name>` and its `account` attribute is the name, so `secret-tool lookup service <label> account <name>` finds it. Listing finds them by a `home` attribute holding `OpenBackupManager-<key>`, as `SearchItems` only matches whole values, and looks in every keyring, as removing does. Secrets cross D-Bus encrypted, with the same Diffie-Hellman exchange and AES as libsecret. Before every read, save or removal it checks whether the keyring is locked, and says so rather than ask to unlock it, which would wait on a prompt nobody might see. `SecretServiceTests` start a D-Bus bus and GNOME Keyring of their own for each test, unlocked with a password as signing in does, so they run without touching the real keyring.
- `DesktopShell` starts a program through the desktop's Explorer, so it runs with the user's normal rights, which the Windows app needs when it was started as administrator (see [Windows app](windows-app.md)). Only Windows has this, so it has no interface in Core.
- `UserPath` adds a folder to the user's PATH, in `HKCU\Environment`, and removes it, keeping every other entry as it was written. It tells Windows the environment changed, so a terminal opened afterwards has it. Installing the Windows app uses it for `obm`, and like `DesktopShell` it has no interface in Core.

## Why

- **Interfaces in Core.** The engine and `obm` will need secrets, and on macOS and Linux `obm` shows notifications itself, so neither interface can live with an app.
- **Notifications are plain data, and what they say lives in the view models.** Each OS's notifier only has to show a title, text and buttons, and every app shows the same notifications, translated once, with their clicks tested on every OS.
- **Notifications use Windows' own toast API, not the Windows App SDK's.** The SDK's show nothing when the app runs elevated ([microsoft/WindowsAppSDK#3595](https://github.com/microsoft/WindowsAppSDK/issues/3595)), as everything does on GitHub's runners, so they couldn't be tested in CI. They also needed three workarounds: the builder didn't escape button labels ([#4996](https://github.com/microsoft/WindowsAppSDK/issues/4996)), its buttons couldn't close a notification without starting the app ([#2960](https://github.com/microsoft/WindowsAppSDK/issues/2960)), and registering needed a DLL only shipped inside the runtime's MSIX ([#6774](https://github.com/microsoft/WindowsAppSDK/issues/6774)). The cost is doing the SDK's registration ourselves: the app's ID, the COM class for clicks, and removing both when uninstalling. It also keeps Platform.Windows free of the Windows App SDK.
- **`obmd` is built for Windows' own framework on Windows.** Platform.Windows needs it for Windows' toast API, and a project for plain `net10.0` can't reference one that needs it. So `obmd`, and `Cli.Tests`, which run it, pick their framework by the OS they're built on, and `obmd` references each OS's platform project only when it's built on that OS, as its packages are, since AOT can't build for another OS. Built on macOS or Linux, `obmd` defines `MACOS` or `LINUX`, as Windows' framework defines `WINDOWS`, and one `#if` calls `AddWindowsPlatform`, `AddMacOSPlatform` or `AddLinuxPlatform`. Anything else checks the OS at run time, with `[SupportedOSPlatform]` so the analyzer checks the callers.
- **The secret store is chosen, never guessed, on Linux.** With lingering on and nobody signed in, gnome-keyring is started but stays locked, so saving fails and reading a secret that's there says it's missing. After an automatic sign-in, reading waits on an unlock prompt. Kopia turns the keyring off on Linux for these reasons, and Git Credential Manager has no Linux default. Windows and macOS default to their own store, as theirs are unlocked whenever you're signed in at the desktop, which is when the engine usually runs. Over SSH they can't be used either: the login keychain is locked, and Credential Manager has nothing to keep secrets with.
- **The file store is in the state folder, not the config folder.** `config.toml` is meant to be safe to share or keep in a dotfiles repo, so secrets stay out of its folder on macOS and Linux. Windows keeps both in one folder, so sharing that whole folder would share the secrets too.
- **Credential Manager, as Git Credential Manager uses.** It's built into Windows, encrypted for the user with DPAPI, and visible and removable in Control Panel. `CredentialManager` is based on Git Credential Manager's store (MIT licence, credited in `THIRD-PARTY-NOTICES.txt`), keeping what it learned: secrets as UTF-16, as Windows' own tools read them, and kept to this computer rather than roaming with the user's account.
- **The Keychain through `/usr/bin/security`, not Security.framework.** Builds aren't signed with a Developer ID, so each update has a new signature, and macOS refuses it an item the previous build saved through Security.framework, or asks for the login keychain's password (probed on macOS 15.8). An item the tool saved belongs to the tool, so every build reads it without a prompt. go-keyring, which gh and Kopia use, does the same for the same reason. The cost is that any program running as the user while they're signed in can read them through the tool too. If builds are ever signed with a Developer ID, the engine moves to Security.framework, saving each secret again once.
- **Keychain secrets are saved as base64.** `security -i` splits each line with its own quoting and can't take a newline in one, and `find-generic-password -w` prints a secret with anything outside printable ASCII as hex, which can't be told apart from a secret that's hex text. Base64 always comes back as it was saved. It's quoted all the same, as an empty secret would leave `-w` with no value, and the tool would ask for one. Keychain Access shows the base64 rather than the secret.
- **Secret Service over D-Bus, not through libsecret or `secret-tool`.** go-keyring, which gh and Kopia use, talks to it over D-Bus too, with no native library to install. libsecret is a C library built on GLib, so reading the keyring's `Locked` property through it takes several native calls, and it isn't always installed on a server. `secret-tool` can't say whether the keyring is locked, and reports a secret in a locked one as missing (probed on Ubuntu 26.04), which is exactly what the engine has to tell apart.
- **No package does what the secret stores do (checked Nov 2026).** On macOS, every one found saves through Security.framework, which unsigned builds can't read after an update: ktsu.CredentialCache, Darkspyre.SecureStore, Devlooped.CredentialManager (Git Credential Manager's stores, repackaged), KeySharp and MSAL's cache extensions. On Linux they load libsecret or run `secret-tool`, apart from Ace4896.DBus.Services.Secrets, which is built on Tmds.DBus.Protocol as ours is, but unlocks a locked keyring, which can show a prompt, takes no cancellation token, and only connects to the session bus, so the tests' own bus can't be used. On Windows, Meziantou.Framework.Win32.CredentialManager comes closest, but a read that fails for any reason comes back as not found, so over SSH it would say a secret is missing rather than why.
- **The `Run` key for starting at login.** It needs no admin rights, and it's what Windows' Startup apps lists and lets the user turn off. A scheduled task can start an app at login too, but it's for running elevated or on a schedule, which the app doesn't need. A packaged app's `StartupTask` needs the app to be packaged, which it isn't.
- **Turning it off in Startup apps is left to Windows.** Windows doesn't remove the entry, but marks it off under the same name in `Explorer\StartupApproved\Run`, and skips it at login. So the app can write its entry at every start without undoing that, as long as the name stays the same. The app never reads or writes that mark, as it isn't a documented API.
- **Moving secrets copies them before it removes any.** Removing them first could leave the engine on an empty store, and changing the setting last of all could leave it reading the old store once they're gone from it. In this order, wherever it stops, the setting points to a store that holds them all. What the new store already has for this home is kept, as it can be the only copy of a secret, such as after `secret-store` was changed by hand.
- **Names from the home folder's key.** Copies with different homes run side by side, so they mustn't share secrets. Moving a home to another folder leaves its secrets behind, so you'd sign in again.
- **`UserPath` edits the registry value itself, with care, not through .NET.** Windows has no call for adding to PATH, so installers, rustup, Scoop and Chocolatey all read, change and write the value the same way. .NET's `Environment.SetEnvironmentVariable` for the user expands `%VARIABLE%` entries and writes the value back as a plain string, fixing them. `UserPath` reads the value unexpanded and keeps its type, adds by appending, removes only whole entries that are our folder, leaves the rest as written, and doesn't touch a value that isn't a string, as rustup does, since Chocolatey and VS Code's installer overwrite one. `UserPathTests` covers each of these.
- **Windows' own integration code is ours too (checked Nov 2026).** No current library shows toasts for an unpackaged app running elevated with NativeAOT: DesktopNotifications is archived, and the others wrap the archived Community Toolkit's. AutoLaunch, for the `Run` key, marks its entry as allowed in `StartupApproved\Run` every time it's turned on, overriding someone who turned it off in Startup apps. The Windows App SDK's `EnvironmentManager.AppendToPath` finds an existing entry with a case-sensitive substring match, appends without a `;`, and always writes `REG_EXPAND_SZ`, which `UserPath` avoids. Nothing packages starting a program through Explorer. CsWin32 can now generate the COM interfaces that `DesktopShell` and `NotificationActivator` declare by hand.
