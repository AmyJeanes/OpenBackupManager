# Windows app

The Windows app is a native WinUI 3 tray app, in `src/OpenBackupManager.App.Windows`.

## How it works

- It's unpackaged (a plain folder with an exe, no MSIX) and carries its own copy of the Windows App SDK, so nothing else needs installing. It runs on Windows 10 1809 or later.
- `Program` builds the app's services in one place, with Microsoft.Extensions.Hosting and dependency injection, after the single-instance check so a copy that hands over builds nothing. `Tray`, `AppNotifications` and `Updater` are created once the UI thread is running, since they need it, and windows are created from the services each time they open. `AppActions` is what the tray, notifications and windows ask the app to do: open a window, quit, restart to update or show the settings file. Quitting stops the engine if the app started it, then disposes the services, which takes the tray icon down.
- The app logs through Microsoft.Extensions.Logging to `logs\app-<date>.log` in the home folder, written by Serilog. A new file starts each day and whenever one reaches 10 MB, and only the newest 7 are kept, so the logs never take more than 70 MB. Each line has the time, the level and the class that logged it. Tokens and passwords are held in Core's `Secret`, which logs as `***`, so they never reach the logs. A copy that hands over to a running one exits before logging anything, so only one copy writes to a home's logs.
- The main window uses the Mica backdrop and extends its content into the title bar.
- `Tray` puts the icon in the notification area through WinUIEx's `TrayIcon`. Left-click opens the status flyout, double-click opens the main window, and right-click opens a menu with Sync all now, Pause, Open, Show test notification, About and Quit. Debug builds also get an Icon state submenu for trying each status icon.
- The status flyout, `StatusFlyout`, is a small borderless window with the status, Sync now and Open. It opens centred on the tray icon, just clear of the taskbar, or just clear of the icon in the hidden icons popup. It slides out from behind the taskbar, follows the Windows mode like the tray icon, and closes when it loses focus or on Esc. Its status and Open come from `StatusViewModel`, which the tray icon and its tooltip follow too.
- `EngineConnection` keeps the app connected to the engine for its home (see [Engine and command line](engine.md)). If none is running, it starts `obmd.exe` from beside the app, with the same `--home` and `--started-by-app`, its console hidden. When the connection ends, as when the engine crashes, it tries again after 1 second, doubling up to a minute, and back to 1 second once a connection has lasted a minute. Until it's connected, the status says Starting or Can't reach the engine instead of how syncing is going. A smaller line under it says why when someone can do something about it: an engine started by another user or as administrator, or another version still running. The app references the Daemon project, so `obmd.exe` is built beside it.
- The app icon, `Assets/AppIcon.ico`, is used for the exe, the window and its taskbar button. It's full colour, so one version has to read on both light and dark taskbars. `Assets/AppIcon.png` is its 256-pixel size, for showing it larger in the app, since an image control only shows an `.ico`'s first, smallest size. `AppIcons` has the paths to both. Every window sets the icon, including the flyout, which Task Manager lists under the app.
- The About window shows the version and links to the repo, licence and third-party notices. It also shows when updates were last checked, with a button that checks now, or restarts to install an update that's waiting. In a dev build the button is greyed out, so the layout matches. Its text and button come from `AboutViewModel` in the shared [view models](view-models.md).
- The tray icon is single-colour and shows one of five states: idle, syncing, paused, needs attention and error. Each state has an SVG for a light taskbar and one for a dark taskbar in `Assets/Tray/`, and the icon switches when the Windows mode changes.
- Launching the app opens the status flyout rather than the main window, which is the full view and opens from Open. Closing the window destroys it, and the tray keeps the app running. Quit stops the engine if the app started it, removes the tray icon and exits.
- One copy runs for each home folder. Launching the app again hands over to the running copy, which opens its flyout, and the new copy exits.
- Started as administrator, as with Run as administrator, the app starts itself again without admin rights through Platform.Windows' `DesktopShell`, and exits. If it can't, it says it doesn't need admin rights, and exits. When Windows only gives the user admin rights, as with UAC off, it runs as normal, as the engine does. `.github/scripts/Test-RunningAs.ps1` checks on CI that it explains, as the runners can't start it again (see below).
- Core's `AppHome` picks the home folder, where everything the app keeps will go: `--home`, then the `OBM_HOME` environment variable, then `%LocalAppData%\OpenBackupManager` for an installed copy, or `%LocalAppData%\OpenBackupManager-Dev` for one that wasn't installed, such as a build run while developing. Its config, state, logs and cache all go in it, through Core's `AppPaths` (see [Configuration and files](config.md)). The single-instance lock is named from it, so copies with different homes run side by side, each with its own engine. A copy that wasn't installed calls itself "Open Backup Manager (dev)" in its tooltip, flyout, window title and notifications.
- Velopack installs it per user into `%LocalAppData%\OpenBackupManager.App`, with a Start menu shortcut and no admin rights. Each architecture, x64 and ARM64, is its own Velopack channel, so an install only updates to its own build.
- `tools/Publish-App.ps1` publishes the app, `obmd` and `obm` into one folder, each compiled ahead of time with NativeAOT, so none needs .NET and each starts quickly. The app and `obmd` go in the folder, and `obm` alone in `bin`, so it can go on PATH without the rest.
- `Updater` checks GitHub Releases when the app starts and every 6 hours, and downloads an update in the background. It then shows an Update available notification whose Restart now installs it, or it installs when the user quits or next starts the app. Restarting to update keeps the copy's home, which Velopack's restart would otherwise drop with the rest of the command line. The first time a newer version starts, however it was installed, an Update installed notification links to its release notes. It knows by keeping the last version that ran in `last-version` in the home folder. It follows prereleases while running one, unless `[updates] prereleases` in `config.toml` says otherwise. Copies that weren't installed by Velopack don't check. For trying updates out locally, an `update-source` file in the install folder, or the `OBM_UPDATE_SOURCE` environment variable, points it at a folder or URL instead of GitHub, and About marks the version with (test updates). The file lasts through updates but goes when the app is uninstalled or reinstalled.
- Uninstalling runs the app's uninstall hook first, which removes its notification registration and clears its notifications. Its secrets in Credential Manager stay, as its data folder does, so a reinstall carries on where it left off.
- When an error nothing caught is about to close the app, `CrashCapture` logs it and writes a report through Core's `CrashReports`. WinUI's `UnhandledException` hears of errors in XAML events such as clicks, .NET's of errors on other threads, and `UiSynchronizationContext` of errors in work queued for the UI thread, including async code resuming there. Reports go in the state folder's `crashes` folder as `crash-<time>-app.txt`, with the error, the version, the OS and up to 100 of the run's last log lines, read from where the log had got to when the run started, and the newest 10 are kept. Errors in tasks nothing waited for don't close the app, and are logged as warnings.
- Some crashes skip every .NET handler, such as one inside Windows' own code, a stack overflow or `Environment.FailFast`. So each run writes an `app.running` file in the state folder with its process ID, start time, version and where its log starts, which a clean Quit, Restart to update, Windows signing out or shutting down, or a crash report removes. If the next start finds it, Core's `CrashEvents` looks in the Application event log for what Windows recorded about that process: Application Error 1000 for a crash or Application Hang 1002 for an app ended while it wasn't responding, plus .NET's own 1025 or 1026 entry with its message and stack when there is one. Windows' entries can be turned off, as they are on GitHub's runners, so .NET's entry will do on its own. Windows Error Reporting writes Windows' entries, so they name the process in their data, while the crashing process writes .NET's itself, so it's the entry's own process. Both must also name the app's exe, since Windows can give the ID to another process once the app has ended. A report is written from what's found, with the log lines from that run. With no such entry, the run was ended from Task Manager or the power went, so it's only logged.
- The next start shows the newest report it hasn't shown in the Closed unexpectedly window, instead of the flyout, and notes it in a `shown` file in the crashes folder. The engine writes its reports there too (see [Engine and command line](engine.md)), so the app also looks each time it reaches the engine, which shows a report from an engine that crashed while the app was running, once the app has started another. The window's title then says it was the engine. `CrashRestart` asks Windows to start the app again with its home after a crash, which Windows only does once it has run for 60 seconds. Debug builds have a Crash submenu in the tray menu for trying each kind: on the UI thread, in a click, on another thread, failing fast, and hanging.
- When Windows signs out, restarts or shuts down, `SessionEnd` hears it and quits, though without installing a waiting update, which Windows could cut off part way, so that installs at the next start. A window app gets no signal for this as a console one does, only `WM_QUERYENDSESSION` and then `WM_ENDSESSION` sent to each of its top-level windows, after which Windows ends it without anything else running. The flyout's window hears it, since it's open for as long as the app runs, while the tray icon's window is message-only and doesn't.
- The installed app starts at login through Platform.Windows' `RunKey`, unless `start-at-login` in `config.toml` says otherwise, which `StartAtLoginSetting` applies at each start and as soon as the file changes. Left out, only the installed app's own home, `%LocalAppData%\OpenBackupManager`, starts at login, so dev builds, test copies and copies with another home never add themselves. Each home is its own copy, so two homes with it on start two copies. `AppHome` decides by the folder, as the app passes its home on when it restarts. The entry starts the exe the app is running from with its home and `--at-login`, which starts it in the tray without opening the flyout, and a copy started that way while one is already running only exits. Uninstalling removes the entries for every home. The exe's name and publisher are set, as Startup apps shows them.
- Notifications, secrets and starting at login come from Platform.Windows, through Core's interfaces (see [Platform layer](platform.md)).
- `App.Windows.UITests` starts the app with a temporary `--home`, so it runs beside any other copy, and drives it through UI Automation with FlaUI. It takes over the desktop, so its tests are in the `Sandbox` category and only run when picked, as CI does.
  - Windows won't let a background process bring a window to the front unless that process had the last keyboard or mouse input, so the tests press Alt themselves first. The normal app doesn't need this: the click or launch that opens it gives it that permission.
  - GitHub's Windows runners start with windows that won't give up the foreground, so CI closes them first with `.github/scripts/Clear-Desktop.ps1`. It also stops the runner's agent opening WSL's update prompt mid-run: the agent runs `wsl.exe` every 30 seconds, and on the ARM64 image, where WSL can't run, that sometimes opens the prompt.
  - The tray tests find the app's icon by its window and ID, as Windows does, rather than by name, since a copy that was ended leaves its icon behind until the mouse passes over it.
  - The notification tests find notifications in the notification centre, since they don't pop up with Do Not Disturb on, as it is on the runners.
  - A failed test attaches a screenshot to the test results, which CI keeps.
  - `InstallTests` installs, updates and uninstalls the app as a user would, from versions 0.0.1 to 0.0.4 that CI's Install and update job packs with `tools/Publish-TestUpdate.ps1`: the Update available notification, About's Check for updates, including when it fails, and Restart to update, the Update installed notification, installing on Quit and when the app next starts after it was ended, and uninstalling, after which nothing should be left. It also checks the installed app adds its start-at-login entry and that uninstalling removes it. It replaces the installed app, so it's Explicit and only runs when asked for.
  - `EngineTests` check the app starts its engine and says once it's connected, that Quit stops it, including after the app was ended and started again, but leaves one started by hand running, that an engine that ends is started again, that an engine's crash report is shown once the app reaches the engine again, and that one of another version is explained.
  - `InstanceTests` hold the app's lock as a copy in another session would, and check a launch says the app is already running there, or exits quietly at sign-in.
  - `StartAtLoginTests` check a copy that wasn't installed doesn't add itself, that `start-at-login` adds and removes its entry as the file changes, and that a start with `--at-login` stays in the tray. A real sign-in starting the app was checked in Windows Sandbox.
  - `CrashTests` crash the app on the UI thread, on another thread and by failing fast, and check the next start shows the report once, and that Windows has the restart registered with the app's home. Another sends the flyout's window what Windows sends at sign-out and checks the app quits without the next start counting it as a crash; a real sign-out and restart were checked the same way in Windows Sandbox. Seeing Windows restart it takes over a minute, so that test only runs when picked by name.

## Why

- **People see Open Backup Manager, with spaces.** Start menu and store searches match each word, and screen readers read it naturally. The joined `OpenBackupManager` stays wherever it's an identifier: the repo, the pack ID, and the install and data folders.
- **Only the WinUI package, not all of `Microsoft.WindowsAppSDK`.** The full package also brings the SDK's AI, machine learning and search parts, which take the app from 94 MB to 154 MB. `Microsoft.WindowsAppSDK.InteractiveExperiences` is referenced directly because the WinUI package asks for a version of it that was never published.
- **WinUIEx for the tray icon.** WinUI has none of its own. WinUIEx's needs no window, takes any WinUI flyout as its menu, and accepts SVG icons. H.NotifyIcon was the alternative, but WinUIEx did everything we needed and its window helpers are useful elsewhere too.
- **CsWin32 for the Windows APIs that WinUI and WinUIEx don't cover.** It generates the declarations, structs and constants from Windows' own metadata for the names in `NativeMethods.txt`, which is Microsoft's recommended way to call them, so `NativeMethods.cs` only holds our helpers.
- **A double-click doesn't wait to rule out a single click.** Waiting for the double-click time (500 ms by default) would slow every flyout open, which otherwise takes about 20 ms. The first click opens the flyout, and the double-click opens the main window, which takes focus and closes it.
- **Serilog writes the log files.** .NET's logging has no file logger of its own. Serilog's rolls by day and size and keeps a set number of files. NLog does the same but is set up through its own config files, and a logger of our own would leave rolling, locking and flushing to us. Everything else logs through `ILogger`, so only `Program` knows about Serilog.
- **One copy for each home, through a global mutex and `AppInstance`.** The app starts and stops its home's engine, so two copies for one home would fight over it. Core's `ProcessLock`, the engine's own kind of lock, is global, so it covers every session. `AppInstance` only finds a copy of the same exe in the same session, but it also hands the launch over so the running copy can open its flyout, which a mutex can't. A copy that finds the lock held with nothing to hand over to says the app is already running in another session or from another copy, or exits quietly when started at sign-in. That only happens when one account has several sessions at once, as Windows Server can allow, or when two accounts or exes are given the same `--home`. `Program.cs` replaces WinUI's generated `Main` so the check happens before anything is created. The new copy has to pass its right to take focus to the running copy, since Windows only gives it to the app the user just launched.
- **NativeAOT for all three programs.** They start faster and use less memory than with .NET's runtime, which matters for a tray app and an engine that run all day, and `obm` is one file that can sit alone on PATH. CI tests what ships: the UI tests and `obm`'s and `obmd`'s run against the folder `Publish-App.ps1` publishes in Debug, given in `OBM_TEST_PUBLISHED`, and InstallTests against the Release build. Locally, tests run the build, which is the same code.
- **Quit stops only an engine the app started,** as quitting OneDrive or Dropbox stops syncing, while one started another way, such as at sign-in by Task Scheduler, keeps running. The engine remembers it was started with `--started-by-app` and says so in `status`, so a copy started after the app crashed knows too. A file holding the engine's process ID could be left behind by a crash, and the ID reused.
- **`obmd` is started through the shell,** so it inherits none of the app's handles. Otherwise whatever started the app, such as `dotnet test`, would wait for the engine to exit too, as it would still hold that program's output open.
- **Started as administrator, the app starts itself again without admin rights.** The engine it starts would run as administrator too, which the engine refuses (see [Engine and command line](engine.md)), and Windows doesn't show an app's notifications while it runs as administrator. A process can't give up its admin rights, so `DesktopShell` asks the desktop's Explorer, which runs with the user's normal rights, to start the app, as [Raymond Chen shows](https://devblogs.microsoft.com/oldnewthing/20131118-00/?p=2643). The new copy gets Explorer's environment rather than the app's, so it's always given its home with `--home`. It's also given `--restarted`, so if it still has admin rights, as when Explorer has them too, it explains rather than starting yet another copy. When Explorer runs as another user, as after Run as different user, it would start the app as them, so the app explains instead. That's the case on GitHub's runners, where Explorer belongs to the runner's own account, so CI can only check the explaining.
- **The update notification isn't one that stays on screen until it's clicked.** The update installs on the next restart or Quit anyway. That kind is kept for problems that need the user.
- **The install folder isn't the data folder.** Velopack always installs to `%LocalAppData%\<pack ID>` unless an install is told otherwise, and reinstalling, as a winget upgrade does, deletes that folder. So the pack ID is `OpenBackupManager.App`, which keeps it clear of the app's data in `%LocalAppData%\OpenBackupManager`. The data stays in Local rather than Roaming AppData because it's tied to this device. The pack ID can't change later without stranding existing installs.
- **Checking for updates by hand is in About, not the tray menu.** The app checks by itself, so it's rarely needed, and About shows the result next to the version instead of in a notification, which still works with notifications turned off.
- **Self-update stays on for winget installs.** winget runs the same Setup, and Velopack keeps the version in the uninstall entry current as it updates, so once the app has updated itself, winget sees it as up to date.
- **Starting at login runs the exe in `current`, not Velopack's launcher.** Velopack updates `current` in place, so the path lasts through updates, and its Start menu shortcut points there too. The launcher in the install folder, named after the app's title, only starts that exe through `Update.exe` with the same arguments, which is two more processes at every login.
- **Starting at login doesn't open the flyout.** Nobody asked for it, and it would take focus from whatever the user opened first.
- **There's no portable build.** Setup already installs per user with no admin rights, which is the usual reason for one, and the app belongs to the system it runs on: it starts at login, registers for notifications, keeps secrets in Credential Manager and keeps its data in `%LocalAppData%`. A portable copy also counts as installed, so it would share the installed copy's home. Velopack's portable zip is turned off with `--noPortable`.
- **Work for the UI thread is queued through `UiSynchronizationContext`, not `DispatcherQueue.TryEnqueue`.** An error that leaves a DispatcherQueue callback ends the app straight away as a stowed exception (0xC000027B), without WinUI's or .NET's handler hearing of it, so it would close with no report. The context reports the error first, without catching it, so Windows still sees the crash. Code that needs the UI thread keeps `SynchronizationContext.Current` from when it was created there and posts to it, and `BannedSymbols.txt` makes the build refuse `TryEnqueue` anywhere else.
- **Crashes outside .NET are found from the event log at the next start, not caught as they happen.** Catching them needs a native handler outside the process, such as Crashpad, as Chrome and Electron apps use, which is a native part for each OS and usually a server for the dumps. What Windows records is enough to say what failed and where, and Export diagnostics can add the event log entries later, as PowerToys' bug report tool does. The `running` file can't tell a power cut from a crash, which is why a report needs Windows' entry.
- **Accepted limit: a crash before the app has set up its crash handling isn't reported,** such as one while it's choosing its home or building its services. Windows' entry is in the event log, and the restart only applies to a copy that has run for a minute anyway.
- **A crash closes the app rather than carrying on.** After an error nothing expected, what the app holds can't be trusted, so it closes and Windows starts it again cleanly. Windows doesn't restart it after an update or a restart of Windows, which aren't crashes.
- **Windows are destroyed when closed, not hidden,** so the app stays small while it sits in the tray.
- **The tray icon and flyout follow the taskbar's theme, not the app's.** Windows lets the taskbar (Windows mode) and apps (app mode) differ, and both belong to the taskbar. Windows' own tray flyouts and EarTrumpet's do the same.
- **The flyout uses Windows' blur with one colour over it, not WinUI's acrylic.** WinUI's acrylic adds a luminosity layer that turns dark backgrounds solid black or makes light ones too pale. The colours (`#232323` at 77% for dark, `#E3E3E3` at 86% for light) were measured from EarTrumpet's flyout over black and white, which reads well on any background.
- **Windows stay cloaked until they're drawn.** A newly shown window is blank until WinUI's first frame reaches the screen, and the title bar lays itself out again a frame later. A cloaked window is still drawn but not put on screen, so `FirstDraw` keeps a new window cloaked until its layout has settled and Windows has shown that frame. The flyout is created once and cloaked again when it closes, so later opens are instant, and status and theme changes are applied while it's cloaked.
- **The flyout finds the tray icon by asking with each of the app's windows.** WinUIEx doesn't expose the window its icon belongs to, which `Shell_NotifyIconGetRect` needs. Using the icon's position rather than the pointer's keeps the flyout in place when the icon is opened from the keyboard. If the icon can't be found, the flyout opens in the corner by the notification area.
- **The flyout is sized for the icon's display.** Its sizes are in device-independent pixels and converted with that display's scaling. It's placed on that display before it's first drawn, and if Windows rescales it after a move between displays with different scaling, it puts the size back. It's 140 pixels tall unless its content needs more, such as the reason the engine can't be reached, which it measures each time it opens.

## Accepted limits

- **It only builds on Windows.** WinUI's XAML compiler is Windows-only, so `Directory.Solution.targets` leaves out projects with `.Windows` in their names on other OSes, and CI's format check and CodeQL run on Windows. In WSL, Linux builds can seem to work because WSL runs Windows programs such as the XAML compiler through interop; turn interop off to test properly.
- **IntelliSense outside Visual Studio needs a workaround.** C# Dev Kit's background build skips WinUI's XAML step, so the project adds it back until [microsoft/vscode-dotnettools#2990](https://github.com/microsoft/vscode-dotnettools/issues/2990) is fixed. It relies on an internal WinUI target name, so a WinUI update could break the build until the line is updated.
- **On Windows 10, Mica falls back to a plain background.** Mica is Windows 11 only.
- **The first time the flyout opens after launch, its slide can stutter.** Warming it up fully would mean activating it at startup, which would take focus from whatever the user is doing.
- **The main window opens without Windows' zoom animation.** Windows plays it when a window is shown, while the window is still blank, and uncloaking doesn't animate.
- **Dragging the main window lags a little behind the mouse.** WinUI 3 draws the window's content separately from Windows drawing its frame, so they don't move in step. Other WinUI 3 apps such as PowerToys Settings do the same, and there's nothing to change on our side ([microsoft/microsoft-ui-xaml#11096](https://github.com/microsoft/microsoft-ui-xaml/discussions/11096)).
- **A silent reinstall from outside the app leaves it closed.** IT tools and other package managers upgrade by running Setup silently, which closes the running app before installing, and after the install hooks closes anything running from the install folder, so the app can't start itself again. Silent Setup has no option to start it. winget won't do this: its manifest will set `UpgradeBehavior: deny`, so winget and tools built on it refuse to upgrade the app, and `RequireExplicitUpgrade: true`, so `winget upgrade --all` skips it instead of reporting the refusal as a failure. Once the app starts at login, it comes back at the next sign-in.
- **A hang ended from Task Manager while only the tray icon shows isn't reported.** Windows only records a hang it handles itself, when a window that isn't responding is closed and its prompt's Close the program is chosen. Task Manager ends a background app without any record, so the next start only logs that the run ended without quitting.
- **From the hidden icons popup, the flyout opens behind the popup.** The flyout sits just below the taskbar in the stacking order so it slides out from behind it, and the popup sits above the taskbar. OneDrive's flyout does the same.
- **Crash reports from a release name the methods but give no file or line numbers.** Only symbol files have those, and publishing makes none, as NativeAOT's are bigger than the programs.

## Checking by hand

CI can't see display scaling, effects or the taskbar, so changes to the windows or the tray need these checking on a real desktop:

- Light and dark Windows mode, switched while the app is running.
- Animations off, and transparency effects off (Settings > Accessibility > Visual effects).
- 150% scaling on the display with the taskbar, both switched while the app is running and at launch, with another display at a different scaling.
- The tray icon on the taskbar, in the hidden icons popup, and near each end of the taskbar.
- Launching the app again from the Start menu while it's running, with the main window open and closed: the flyout should open and take focus.
- The test notification's name and icon, as it pops up and in the notification centre.
- For changes to text, a dev build run with the `OBM_UI_CULTURE` environment variable set to `qps-ploc`, with each window, the tray menu and the test notification opened. All text should be accented and in brackets: plain text isn't coming from `Strings`, and text that's cut short needs more room.
- For changes to crash handling, a hang: open About, choose Crash > Hang from the tray menu, close About, and choose Close the program on Windows' prompt. The next start should show a report from what Windows recorded. A UI test can't, since the prompt is Windows' own and GitHub's runners keep no record of hangs.
- For changes to starting at login, signing out and in again with it on: the app should be in the tray with no flyout, and turning it off in Settings > Apps > Startup should keep it from starting, even after the app has started again since.
- For changes to starting as administrator, a dev build started with Run as administrator: Task Manager's Details tab should show one copy, with No under Elevated (add the column from its header), and the flyout should open and take focus, the engine connect and the test notification show. Windows Sandbox can't, as its account only has admin rights.
- For changes to installing or updating, a build packed as in CI's release job: a dev build running alongside the installed copy, installing it again over a running copy with `--silent`, and uninstalling it from Settings > Apps.

### Trying updates locally

`tools/Publish-TestUpdate.ps1` packs versions into a local feed in the temp folder, the same way as CI's release job. With `-Install`, it also writes the installed copy's `update-source` file, so it checks that feed however it's started, until it's uninstalled.

1. `./tools/Publish-TestUpdate.ps1 -Version 0.0.1-local -Reset -Install` starts a new feed with that version, installs it and starts it. About shows (test updates) after the version.
2. In About, Check for updates should say it's up to date.
3. `./tools/Publish-TestUpdate.ps1 -Version 0.0.2-local` adds a newer version to the feed.
4. Check for updates again: it should download the update, show Version 0.0.2-local is ready to install, and turn the button into Restart to update.
5. Restart to update, or Restart now on the notification, should restart into the new version. To try installing on Quit instead, add another version as in step 3, check, and quit.
6. Uninstall Open Backup Manager from Settings > Apps when done.

## Releasing

1. Push a tag such as `v0.1.0`, or `v0.1.0-alpha.1` for a prerelease.
2. CI's release job builds x64 and ARM64, packs each with Velopack, and uploads them to a draft release called `Release v0.1.0`, marked as a prerelease if the version has a `-`.
3. Write the notes and publish the draft. Installed copies only see published releases, so nobody updates until then.

The repository makes published releases immutable, so a broken release is replaced by a new version, never patched, and a release job can only be re-run before publishing.

To try the release job itself, tag throwaway prereleases such as `v0.0.2-test.1` and `v0.0.2-test.2`, with a version number never used before, since an old tag name may not be reusable and copies that installed it wouldn't update to it again. Delete the releases and their tags afterwards.
