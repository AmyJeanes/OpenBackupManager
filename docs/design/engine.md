# Engine and command line

`obm`, the command line, and `obmd`, the engine that runs in the background. The engine only runs and answers `obm status` for now, and later steps give it work to do.

## How it works

- `src/OpenBackupManager.Cli` builds `obm` and `src/OpenBackupManager.Daemon` builds `obmd`, both with System.CommandLine. They run on Windows, macOS and Linux, and `OpenBackupManager.Cli.Tests` runs the built `obm` and `obmd` on every CI runner, as a user would.
- For macOS and Linux, CI's package-macos and package-linux jobs publish `obm` and `obmd` for x64 and Arm64, and `tools/Pack-Tarball.ps1` packs them with `LICENSE` and `THIRD-PARTY-NOTICES.txt` into `OpenBackupManager-<version>-<runtime>.tar.gz`, with no folder inside, so they can be unpacked straight onto PATH. Each is attested, uploaded with the edge builds and added to the draft release beside the Windows packages (see [Releasing](windows-app.md#releasing)). First, `.github/scripts/test-tarball.sh` runs each as unpacked: it checks the licences are there, starts `obmd`, reaches it with `obm status` and stops it, on the Mac runner it was built on, and for Linux in Debian 12 and RHEL 9 containers, which check-linux runs on each architecture's own runner, as the cross-build images that build them only run on x64.
- package-linux also makes `OpenBackupManager-<version>-<runtime>.deb` and `.rpm` from the same programs, with nfpm's image and `nfpm.yaml`: `obm`, `obmd` and the licences go in `/usr/lib/openbackupmanager`, linked from `/usr/bin`. In check-linux, `.github/scripts/test-package.sh` installs each with apt or dnf in Debian 12, Ubuntu 24.04 and 26.04, RHEL 9 and Fedora containers, which brings what it depends on, and runs `test-tarball.sh` on what's installed. Then it upgrades to it from an older package of the same programs while an engine runs, checks `obm status` says the new version is installed, and checks removing it stops the engine. They're attested, uploaded and released with the tarballs.
- CI's package-docker job builds the Docker image from the `Dockerfile`, copying in the Linux tarballs' `obm` and `obmd` for amd64 and arm64, so it holds the attested files rather than a build of its own. `.github/scripts/test-image.sh` runs each architecture, the Arm64 one through QEMU: as the image's user with a volume and as another user with a folder of theirs, it waits for the healthcheck, reaches the engine with `obm status` through `docker exec`, and checks `docker stop` ends it with 0. On main and version tags, it then pushes `ghcr.io/amyjeanes/openbackupmanager` for both, tagged with the version, plus `edge` for an edge build, and attests it. `release-published.yml` tags a published release's image `latest`, when GitHub calls it the latest release.
- The engine itself is the `OpenBackupManager.Engine` library, which `obmd` runs and `OpenBackupManager.Engine.Tests` runs in-process. `obm` is only a client, which never loads it, and keeps no state of its own.
- `obmd` runs the engine in the foreground with no UI, on the generic host, until Ctrl+C, the console closing, the user signing out, or a service manager stopping it. It logs to `engine-<date>.log` in the logs folder, rotated like the app's logs, and prints the same lines.
- When an error nothing caught is about to end `obmd`, it writes a crash report to the state folder's `crashes` folder, as the tray app does, and the app shows it (see [Windows app](windows-app.md)). An `engine.running` file tells the next start when a run ended without stopping, as one that crashed outside .NET does. On Windows, it writes a report from what Windows recorded. On macOS and Linux, it writes one unless the computer has restarted since, which the boot ID kept in the file tells: Linux's `/proc/sys/kernel/random/boot_id`, or macOS's `kern.bootsessionuuid`. On macOS, Core's `DiagnosticReports` adds the crash report macOS wrote for that process, matched by its process ID and boot: the signal, what sent it and the top of the crashed thread's stack. What the run printed as it ended, which is where a FailFast's message goes, comes from `obmd-stderr.log` in the logs folder on macOS, where the LaunchAgent sends stderr, and on Linux from the journal, through `Journal`'s `journalctl --user _PID=<pid> _BOOT_ID=<boot>`, where systemd sends a service's stderr. With nothing from the OS, the report says it didn't say why, and where else to look, if anywhere. A run that closed within a minute of starting, soon after the last report, gets no new report, only a line in the log. `obm status` lists the reports not yet seen, by the app or `obm crashes show`, without counting them seen itself, so a script running it doesn't use them up. The `shown` file names the newest one seen, so those not yet seen are always the newest, and `obm status` numbers them as `obm crashes list` does. Debug builds answer a `crash` method, for the tests.
- `--home` or the `OBM_HOME` environment variable picks a home folder, as for the app, through Core's `AppHome`, the same for `obm` and `obmd`. Without one, Windows uses the same home as the tray app: `%LocalAppData%\OpenBackupManager`, or `OpenBackupManager-Dev` for a build that wasn't installed, which they find out by asking Velopack, since they're installed beside the app. macOS and Linux use their usual folders (see [Configuration and files](config.md)).
- One engine runs for each home, held by Core's `ProcessLock`: `engine.lock` in the state folder, kept open exclusively, which on macOS and Linux is an `flock`. It's the same file in every session, including SSH, however the home's path is written. A second `obmd` for the same home says the engine is already running and exits with 1.
- The engine listens on a socket for the tray app and `obm`: a named pipe on Windows, named from the home's key, and a Unix domain socket at `run/engine.sock` in the state folder on macOS and Linux. Core's `EngineSocket` says where, and Core's `EngineClient` connects, for both the tray app and `obm`.
- They talk JSON-RPC 2.0, one message to a line, with System.Text.Json's source generator. A client sends `hello` with its protocol and version first, and the engine refuses one whose protocol isn't its own, saying both versions, and closes the connection. `hello` and that reply keep their shape in every version, as they're how two different versions find out. The protocol only goes up once there are releases people use, and until then changes are made in place. Errors have JSON-RPC codes, and the engine's messages are in English. `obm` prints them as they are, while the tray app words the ones it shows itself, from the code, so they can be translated. `status` gives the engine's version, process ID, start time and folders, which `obm status` shows, what started it: the tray app, its service or something else, and the errors and warnings from its latest read of `config.toml`, each with its line, kind and value, so `obm` can word them. Errors and warnings don't change `obm status`'s exit code, as the engine is still running on its last good settings, and a health check that failed would restart it into an engine that won't start. `stop` stops it, closing every connection once it has replied. `migrateSecrets` moves the secrets to another store and replies once they're moved, which `obm secrets migrate` asks for (see [Platform layer](platform.md)). `reloadConfig` has the engine read `config.toml` again and replies with what it found, as `status` gives it, which `obm config reload` asks for. On macOS and Linux, SIGHUP does the same, as it does for most daemons, rather than ending the engine, so closing a terminal that started `obmd` leaves it running. Not on Windows, where .NET maps SIGHUP to the console window closing. Without an engine, `obm status` says so and exits with 1. `obm status`, `obm config reload` and `obm config validate` take `--json`, which prints the engine's reply as it is, indented, so its field names are a contract for scripts, changed as carefully as the protocol, and `JsonTests` pins them. `validate` prints the record `reloadConfig` replies with. When there's no reply, such as with no engine, the error goes to stderr as usual and nothing to stdout.
- `EngineClient` reads replies in the background and hands each to the call with its id, so calls can overlap, and its `Closed` task completes as soon as the engine goes, so the tray app can start it again (see [Windows app](windows-app.md)).
- On macOS and Linux, the engine's `UpdateWatcher` looks at `obmd` every 5 seconds. Once it's been replaced, as an upgrade does, and is the same at two checks in a row, so it isn't still being written, it runs the new one with `--version`. An engine its service started then stops with 75, which systemd restarts without counting as a failure, through `RestartForceExitStatus=75` and `SuccessExitStatus=75`, and launchd restarts as it does any exit but 0. One started another way logs a warning instead, and `status` gives the new version as `installed`, which `obm status` shows. If `obmd` is removed, the engine stops with 0, so neither starts it again.
- `obm update`, on macOS and Linux, updates `obm` and `obmd` from GitHub's releases API (`Releases`): the highest release, and a prerelease only if `[updates] prereleases` says so or this is one, as the app's own updates do. It downloads the tarball for this OS and architecture, checks its SHA-256 against the `digest` GitHub gives for each release file, and unpacks each file beside the one it replaces, as `.<name>.update`, then renames it over it, `obmd` last. The licences are replaced only if they were unpacked there too. Then `UpdateWatcher` restarts a service's engine into it, and `obm update` waits up to 30 seconds for a new process to answer. A folder it can't write to, a build of your own (0.0.0) and an `obmd` that isn't beside `obm` are refused before anything is downloaded. The .deb and .rpm have an `installed-by` file beside the programs saying `deb` or `rpm`, which CI writes for each, and the image's `Dockerfile` adds one saying `docker`, so `obm update` says how to update those instead. `--check` only checks. `OBM_UPDATE_SOURCE` points it at another server, where it updates a 0.0.0 build too, so `UpdateTests` run it against `FakeGitHub`, a local server answering as GitHub does, and a service test checks the restart. On Windows it's left out of `--help` and says the app updates itself.
- The tray app starts `obmd` with the hidden `--started-by app`, and a service with `--started-by service`, which the engine keeps in memory, so the app's Quit stops only an engine it started.
- `obm service install` keeps the engine running on macOS and Linux, through the OS's service manager, as the user. `EngineService` finds `obmd` beside `obm`, and `LaunchAgent` and `SystemdService` write what each OS's manager needs:
  - **macOS:** a LaunchAgent, `io.github.amyjeanes.openbackupmanager.engine.plist` in `~/Library/LaunchAgents`, loaded into the user's session with `launchctl bootstrap gui/<uid>`. `RunAtLoad` starts it at sign-in, and `KeepAlive` with `SuccessfulExit` set to false starts it again if it crashes or fails. `StandardErrorPath` sends its stderr to `obmd-stderr.log` in the logs folder. macOS lists it in Login Items & Extensions, where switching it off stops the engine and keeps launchd from starting it, without launchd saying why. `SMAppService.statusForLegacyURL`, reached through the Objective-C runtime, tells `obm status` and `obm service install` it's off, so they say so.
  - **Linux:** a systemd user service, `openbackupmanager.service` in `systemd/user` in systemd's own `$XDG_CONFIG_HOME`, or `~/.config`, enabled for `default.target` and started with `systemctl --user`. `Restart=on-failure` starts it again. `ExecReload=` runs `obm config reload` from beside `obmd`, so `systemctl --user reload` waits for the engine and fails while `config.toml` has an error, as systemd's documentation asks of a reload, where `kill -HUP` would return straight away.
  - Each home other than the usual folders has its own, named with a key made from its path, and the service gets `--home` with it. Without one, the service gets the `XDG_` folders `obm` sees, as it gets none of the shell's environment.
  - Installing stops an engine started another way, as only one runs for each home, then starts the service and waits until its engine answers. Installing again replaces the service and restarts its engine. Uninstalling stops the engine and removes the service.
  - `obm status` says when the engine isn't running though a service is installed, with the command that shows why. On Windows, both commands are left out of `--help` and say the app starts the engine instead.
  - `ServiceDefinitionTests` check what's written on every OS. `ServiceTests` install with the real service manager, so they're in the Sandbox category, which CI runs: installing, uninstalling, taking over an engine, installing again, and an engine that's killed being started again. CI turns on lingering for the Linux runner, which has no session, so its systemd runs.
- Core's `RunningAs` says whether they were started with rights other than the user's own. On Windows, `obmd` exits with 1 when it has an admin token and Windows has a normal one too. On macOS and Linux, `obmd` and each `obm` command exit with 1 when sudo, doas, pkexec or run0 started them as another user, which they tell from the variables those set. `.github/scripts/Test-RunningAs.ps1` checks both on CI, with a throwaway admin account and silent RunAs on Windows, and with sudo elsewhere.

## Why

- **The lock frees itself if the engine crashes.** The OS closes the file, and with it the lock, when the process holding it ends, however it ends, so the next start never finds a stale lock. A file holding the engine's process ID would stay behind after a crash, and the next start would have to work out whether that ID still belongs to the engine or has been reused by another process.
- **A lock file on every OS,** so a short name, junction or `subst` drive for the home still leads to the same lock. A named mutex on Windows would be named from the path as written, so each spelling would get its own. The engine's pipe and secret names still come from the written path, so a client using another spelling won't find the engine, but a second engine is refused.
- **Others can read the lock file on Windows,** as with Chromium's (`process_singleton_win.cc`), so a backup program or scanner reading the state folder isn't taken for a running engine. macOS and Linux share nothing, as .NET only takes an exclusive `flock` then. Something could still have the file open for a moment, so that `obmd` exits, and whatever started it starts it again: the app after a second, systemd and launchd as they would after a crash. `obmd` doesn't wait itself, or systemd would never see five quick failures and give up while another engine holds the lock. Defender's scans never held it in a probe of about 140,000 opens (Nov 2026).
- **`flock` on macOS and Linux,** as Unix daemons lock. .NET takes an exclusive `flock` when a file is opened with `FileShare.None`.
- **The state folder, not `$XDG_RUNTIME_DIR`,** for the lock on Linux. The state folder is the same in every session, but `XDG_RUNTIME_DIR` isn't set without a login session, as with `su`, cron, some SSH setups and containers. A lock there would be in a different place for those, so it wouldn't stop a second engine.
- **The boundary is the user account.** Each end only talks to the other if the OS says it runs as the same user, so other accounts can't send the engine commands or pretend to be it. It doesn't prove the engine is really `obmd`, but anything running as the user could read the same files and tokens anyway. `hello` only checks versions. Both ends get this from `PipeOptions.CurrentUserOnly`, plus the steps below.
- **On Windows,** the pipe only lets its owner open it, and a client asks Windows who owns it before sending anything. The client does that itself because .NET's check expects Administrators as the owner when the client is elevated, so `obm` in an admin terminal couldn't reach an engine that isn't. It accepts the user, or Administrators when it's elevated too.
- **On macOS and Linux,** each end asks the OS which user is at the other end. The socket file's permissions depend on the umask, so the engine keeps it in a `run` folder only the user can open (`0700`), and won't use one that's a link or someone else's.
- **The engine only listens if nothing else has the name,** through `PipeOptions.FirstPipeInstance`. Without it, .NET on macOS and Linux deletes any socket already at the path and takes it over, even a running engine's. As the engine holds its lock, any socket already there was left by one that crashed, so it deletes that first.
- **The socket sits beside the lock, in the state folder,** for the same reason as the lock. It also means one home's engine is always at the same path.
- **The engine runs as the user, with their normal rights.** That's where the tray app and `obm` look for it, and the files it writes are theirs. Backing up a whole machine or a server needs more rights, and is left to tools made for it, such as restic, Kopia and rclone.
- **`obmd` won't run as administrator when Windows has a normal token for it,** as in a terminal opened as administrator, since Windows makes an elevated process's pipe belong to Administrators, so the tray app and `obm` in a normal terminal couldn't reach it. With UAC off, as the built-in Administrator or over SSH, the admin token is the only one, so it runs.
- **No sudo on macOS and Linux,** since the engine would run as root, writing files the user can't change, and on macOS, where sudo keeps `HOME`, into the user's own folders. `obm` would look for root's engine, which is another home. Real root, as with a root login, `su -` or a container, has none of sudo's variables, and is just another user with its own engine. The variables can be set by hand, but that only stops a mistake, so it's no security check.
- **Service failures start it again, but not stopping on purpose,** as when the user signs out or stops it with `systemctl`. `KeepAlive` set to true would start it again however it ended.
- **No service on Windows,** where the tray app starts the engine at sign-in, and tray app users already have it from then on. The Run key, Windows' version of a LaunchAgent, would only add an engine at sign-in for anyone without the app, and only once someone signs in, which a server never does. A real Windows service needs admin to install, and runs as LocalSystem, or as the user with their password stored in its settings, in session 0, out of reach of their Credential Manager, OneDrive's online-only files, mapped drives and notifications. A Task Scheduler task with no stored password (S4U) has the user's identity but not their keys, so their secrets stay locked. A LocalSystem service that starts `obmd` in the user's session would work, but its exe must live in Program Files, so every update to it needs admin. Anyone who wants `obmd` as a service can wrap it with NSSM or WinSW, and it runs as that service's account.
- **The unit goes where systemd's own `$XDG_CONFIG_HOME` says,** from `systemctl --user show-environment`, since systemd finds user units by that rather than the shell's, which may set it only in a profile systemd never reads.
- **Installing takes over an engine that's running,** rather than leaving it be, since the service's engine would fail to start beside it, and launchd and systemd would keep trying.
- **On macOS, installing and uninstalling wait for launchd to let go of the agent.** `launchctl bootout` returns as soon as it's sent `SIGTERM`, but launchd keeps the job, as `SIGTERMed`, until the engine exits. Until then, a client could still reach the engine as it stops, and `launchctl bootstrap` fails with `5: Input/output error`, so `LaunchAgent` waits until `launchctl print` no longer finds it, for up to 30 seconds, longer than launchd's 20 before it kills the engine (checked Nov 2026). systemd's `disable --now` and `restart` already wait for the engine to stop.
- **On macOS and Linux, `obm` and `obmd` are published side by side,** as the tarball has them, so `obm` finds `obmd` beside itself. On Windows, `obm` alone goes in `bin`, which installing adds to PATH.
- **`obmd` is a program of its own,** rather than a command of `obm`, so `obm` is only ever a client: nothing it runs starts an engine or keeps state.
- **JSON-RPC over a socket,** so programs not written in .NET can talk to the engine too, and the source generator, so it needs no reflection.
- **`--json` prints the engine's records,** rather than a format of its own, so there's one set of names to keep. Errors stay on stderr, with nothing on stdout, as gh, kubectl and docker do, so a script checks the exit code. npm and rclone print a JSON error too, but each has a code a script can act on, which `obm`'s errors don't need while the exit code says it all. Only JSON, as `jq`, PowerShell's `ConvertFrom-Json` and `yq` cover the rest.
- **System.CommandLine's error handler is turned off,** so an error that leaves `obmd`'s command is reported as a crash, rather than printed with an exit code of 1.
- **The generic host's console lifetime stops it, not System.CommandLine's Ctrl+C handling,** since the host also stops on `SIGTERM`, so System.CommandLine's handling is turned off.
- **`WindowsShutdownHandler` stops it when its console closes, or the user signs out or shuts down.** Windows ends the process as soon as each of these has been handled, which the host does straight away, so the engine never got to stop. It waits for the host to stop instead, for up to 5 seconds: Windows' own limit when the console closes, and ours for signing out and shutting down, where Windows would otherwise move on to its screen of apps that are preventing it. The console's own sign-out and shutdown events never arrive, because .NET loads `user32.dll`, and Windows then only tells a process through a window, so those come through `SystemEvents`' hidden window.
- **On macOS and Linux, a run that ended without stopping is only reported if the computer hasn't restarted since,** so a power cut, or a shutdown that didn't wait for the engine, isn't taken for a crash. macOS's `kern.boottime` moves whenever the clock is set, even by a time sync of a second, so it would take those for restarts, and real crashes would go unreported. `kern.bootsessionuuid` only changes at a restart (checked Nov 2026).
- **Linux's stderr stays in the journal, rather than going to a file as on macOS,** so `systemctl --user status` still shows why the engine couldn't start. The next start reads the dead run's lines back, which were there every time in testing, as systemd only starts it again once the crash handler has finished. A journal kept only in memory, rather than on disk as by default, has none, so the report says where to look instead. launchd sends stderr nowhere unless told, so the file loses nothing on macOS.
- **`coredumpctl` isn't read,** only named in the report, as its stacks for `obmd` are addresses with no names. It's only named when `/proc/sys/kernel/core_pattern` hands crashes to systemd-coredump, as on Kubuntu. Stock Ubuntu hands them to Apport, which ignores programs that weren't installed from a package, so there's nothing to point to.
- **A crash report from macOS gives addresses, not names, for `obmd`'s own frames in a release,** as releases ship without `.dSYM` files, which ReportCrash needs to name them. The signal, what sent it and the system frames still say how it ended, and a FailFast's own stack, in `obmd-stderr.log`, names the methods.
- **A run that closed soon after the last report doesn't get another,** as an engine that can't get going would otherwise fill the 10 kept with copies of the first, which says why. launchd starts it again every 10 seconds without limit, while systemd gives up after 5 tries in 10 seconds.
- **`obm crashes report` opens a link to a new GitHub issue, rather than sending anything,** so nothing leaves the computer until the person submits it. Over SSH, or on Linux with neither `DISPLAY` nor `WAYLAND_DISPLAY`, it prints the link instead, as opening it would show it on the computer's own screen, or start a text browser such as w3m in the terminal. Stripe's CLI checks for SSH, and gcloud and Python's `webbrowser` for a display.
- **Redaction leaves the report's header as written,** as it holds nothing personal and a name can be an ordinary word, such as the `ubuntu` a default Ubuntu computer is named. It takes out every value in a web address, as .NET's own HttpClient logs do, rather than guessing which names hold tokens, and doesn't list what it took out, since people should check the report anyway.
- **A link is kept to 6,500 characters as GitHub's sign-in page carries it,** encoded again in `return_to`. Someone who isn't signed in goes through that page first, and GitHub fails once it's about 7,000 characters (tried Nov 2026), well short of the 7,500 VS Code's issue reporter allows, which only works for people already signed in.
- **The link fills in a Markdown crash report template, not the bug report form,** as GitHub puts back a form field filled in from a link whenever it's edited, so the report couldn't be checked and trimmed before submitting ([reported Nov 2026](https://github.com/orgs/community/discussions/212206)). An issue's own body stays editable, as VS Code's issue reporter relies on. The template has the form's headings, so an issue reads the same however it was made, which `BugReportTests` checks, and it can say the exact OS, which the form's dropdown can't take from a link.
- **Logs on the console as well as in files,** so running it by hand shows what it's doing, and service managers such as systemd keep what it prints.
- **Linux builds use .NET's own cross-build images,** which link against an older distro's C library (glibc) in `/crossrootfs`, with the runner's .NET SDK and PowerShell mounted in so the SDK is the one `global.json` names. A program needs at least the glibc it was linked against, so one built on the runner's Ubuntu wouldn't start on Debian 12 or RHEL 9. .NET builds itself this way, and says what's built like this runs back to Ubuntu 18.04.
- **ICU stays a requirement on Linux,** rather than turning on .NET's invariant globalization, which would drop it. Without ICU, .NET can't normalise Unicode, which the engine will need for file names: macOS stores accented letters decomposed, and Windows and Linux composed. Desktop distros have ICU already, and the guide says how to add it to a minimal install.
- **`Pack-Tarball.ps1` writes the tarball itself,** rather than running `tar`, whose options for leaving out the build machine's owners and extended attributes differ between macOS and Linux.
- **The image is Microsoft's chiseled `runtime-deps`,** which has only what a NativeAOT program needs: glibc, ICU, time zones, OpenSSL and certificates. With no shell or package manager there's little to patch, and as the `Dockerfile` only copies files, the Arm64 image is made without QEMU. So there's no start script switching to a `PUID` and `PGID` user, as linuxserver.io's images have, and Docker's own `user` does that.
- **The image runs as its own non-root user unless `user` picks another,** as the engine runs as you everywhere else, and files it writes in mounted folders then aren't root's. `WORKDIR /config` makes the folder as that user, so a new volume starts out theirs.
- **`latest` moves when a release is published, not when its tag is pushed,** as the release is still a draft then, and a NAS often updates its containers by itself. Copying the tag with `docker buildx imagetools create` keeps the digest, so the attestation still applies (checked Nov 2026).
- **No init process in the image.** `obmd` is PID 1 and stops on `SIGTERM` itself. Docker's own `init: true` adds one if a program it starts, such as rclone, ever leaves processes behind.
- **nfpm makes the .deb and .rpm,** both from one file, with no dpkg or rpm tools, as GoReleaser does for Go programs. fpm needs Ruby, and rpmbuild for an .rpm.
- **The package keeps its files in `/usr/lib/openbackupmanager`, linked from `/usr/bin`,** so the rclone bundled later never clashes with the distro's, and the path a service runs stays the same through upgrades.
- **The .deb lists every ICU it's been checked with,** as Microsoft's `dotnet-runtime-deps` does, since Debian names ICU's package by its version. Newer distros' `libssl3t64` provides `libssl3`. The .rpm asks for OpenSSL 3 by its library, `libssl.so.3()(64bit)`, as Fedora's own .NET does, since Fedora 45's `openssl-libs` is OpenSSL 4, which .NET can't use, and `openssl3-libs` has 3 (checked Nov 2026).
- **A distro that moves to a newer ICU can't install the .deb** until that version is added to its list, as with Microsoft's own packages. CI checks the newest Fedora, which tends to move first, and the newest Ubuntu LTS.
- **The package installs no service,** as `obm service install` is for one user and one home, and a package's scripts run as root without knowing whose. Syncthing's nudges every running instance, and Keybase's restarts each user's services through `su`, which takes over 100 lines and an opt-out.
- **The engine restarts itself into an update,** within seconds, so an upgrade is in effect once it's done, rather than waiting for a sign-in. One started by hand only warns, as Chromium asks to be relaunched, since nothing would start it again. A backup never quietly stops that way.
- **`obmd` is checked on a timer rather than watched,** as macOS's file events (FSEvents) sometimes didn't report it replaced or removed when it had been copied there just before, and disposing of the watcher could keep the engine from stopping (Nov 2026). Looking at one file every 5 seconds costs next to nothing, and Chromium checks for its own updates on a timer too.
- **An update is told by `obmd`'s time and size,** rather than reading all of it, as each build's file has its own time, which tar, dpkg and rpm all keep. Reinstalling the same package changes neither, so it restarts nothing.
- **Not on Windows,** where Velopack ends whatever runs from its folder before updating it (see [Windows app](windows-app.md)).
- **`obm update` checks the download against GitHub's own SHA-256 for it,** as Velopack checks Windows packages against its feed. GitHub works it out when a file is uploaded, and releases are immutable, so it can't be changed afterwards. `gh attestation verify` checks more, that the project's CI built it, but needs `gh`, so it stays for anyone who wants it.
- **`obm update` refuses a .deb, .rpm or Docker install,** which their own package manager or image updates, and a .deb or .rpm needs root, which `obm` refuses. Any other text in `installed-by`, as another packager could put there, is named in the message.
- **Nothing checks for updates by itself on macOS and Linux,** as there's no app there to say so, and an engine that updated itself could stop partway through a backup. A script can run `obm update --check`.
- **Each Mac build has its own architecture's runner,** though one Mac can build both, so each is run where it was built.
- **Our own JSON-RPC, not StreamJsonRpc (checked Nov 2026).** StreamJsonRpc can send one JSON message to a line, but its System.Text.Json formatter is marked as needing dynamic code, so NativeAOT builds would have to suppress the warnings, and it brings about eight packages, such as MessagePack, Nerdbank.Streams and Newtonsoft.Json, to replace about 150 lines. It also reports a method's exception as -32000, which is our protocol mismatch, with .NET's stack trace unless that's overridden, and has nothing like `hello` having to come first. CurlyRpc fits better on paper but was new and before 1.0. Both are worth trying again once the engine needs progress and cancellation, which StreamJsonRpc sends as LSP's `$/progress` and `$/cancelRequest`; if neither fits then, ours adds the same conventions. The transport stays ours either way, as no library has its rules: the private socket folder, refusing a link, listening only if nothing else has the name, and letting an elevated `obm` in.
- **Installing the service, the engine's lock and stopping it are ours too (checked Nov 2026).** Redpoint.ServiceControl only installs system-wide services, which need root. AutoLaunch's LaunchAgent doesn't escape its arguments or start the agent, and on Linux it writes autostart files rather than a systemd unit. The single-instance packages use a mutex and a pipe on Windows only, and none uses a lock file. The generic host's console lifetime doesn't handle a console closing, and returns at once from the signals it does handle, which lets Windows end the process before the host has stopped, so `WindowsShutdownHandler` waits for it.
- **Third-party notices are made by our own `tools/NoticesGen` (checked Nov 2026).** ThirdLicense, nuget-license, ThirdPartyLibraries and dotnet-project-licenses, tried on the engine, all list build-only packages such as the NativeAOT compiler, none works per runtime, most link to each licence rather than including its text, and none puts packages with the same text together. dotnet-project-licenses also needs .NET 7, and ThirdPartyLibraries keeps a repository of licences to maintain and missed the packages that come through project references.

## Accepted limits

- **On Windows, stopping is cut off after 5 seconds.** That's Windows' limit when the console closes, and ours when the user signs out or shuts down, so a slow stop never leaves them waiting on Windows' screen of apps preventing it. Later steps' work has to stop within that, or be safe to cut off.
- **An engine run as administrator can only be reached as administrator.** Windows makes an elevated process's objects belong to the Administrators group rather than the user, so a client that isn't elevated is refused. `obmd` only runs as administrator when Windows has no normal token for it, so this only comes up when an admin starts it over SSH and then uses the tray app at the desktop.
- **A Unix socket's path has a limit,** 103 bytes on macOS and 107 on Linux, in UTF-8, so a character outside ASCII takes 2 to 4 of them. It covers the whole socket path, and `/run/engine.sock` takes 16, so a `--home` path over about 87 bytes on macOS or 91 on Linux can't have an engine. It says so and suggests a shorter one.
- **macOS won't run them from a browser download,** which it quarantines, since they aren't signed by Apple. The guide shows how to remove the quarantine, or to download with `curl`, which doesn't add it.
- **`obm update` waits for the engine of the home it was given,** so for an engine that runs another copy of `obmd`, such as from a package beside a tarball, it waits the 30 seconds and says it didn't come back.
- **An engine started by hand runs the old version after an upgrade until it's restarted,** as nothing would start it again. The log and `obm status` say so.
- **A service runs `obmd` from where it was when it was installed,** so after moving them, `obm service install` has to be run again. Package managers that move them on each update will need theirs to point at a path that stays the same.
- **The service keeps the `XDG_` folders `obm` saw when it was installed.** It doesn't read the shell's profile, so if they change later, `obm` looks for the engine in the new folders while it runs in the old ones. Running `obm service install` again catches it up.
- **An engine that fails as it starts is started again every 10 seconds on macOS,** which is launchd's least, for as long as it fails. systemd gives up after 5 tries in 10 seconds, its default, and `systemctl --user status` says so. `obm service install` waits up to 30 seconds for the engine, but on Linux stops waiting once systemd gives up.
- **The Docker image is for Linux hosts.** Docker Desktop on Windows and macOS shares folders with its Linux in ways that don't reliably report changes, so the guide says not to use it there.
- **Finding no engine takes a moment.** A client waits up to its timeout, 2 seconds for `obm status`, since an engine may be starting, and a socket left behind by a crash looks the same as one that isn't ready yet.

## Checking by hand

CI checks stopping with `SIGINT` and `SIGTERM` on macOS and Linux. On Windows, a test would have to give up its own console to send Ctrl+C or close another's, or sign out, so there, run `obmd --home <a test folder>` and check `Engine stopped` is logged after each of these, as was checked in Windows Sandbox:

- pressing Ctrl+C
- closing the console window
- signing out
